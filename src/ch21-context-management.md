# 21 上下文管理：长任务为什么会跑偏

## 从一个问题开场

让 Agent 排查"续航掉得快"的原因。前十轮它有条不紊：读电耗数据、查手册、比对气温。到第四十轮，它开始重复查已经查过的数据，忘了用户最初说的"只看最近一个月"，最后给出一个和第五轮的发现相矛盾的结论。

模型没有变笨。变的是它每一轮读到的东西：第 19 章的循环里，消息列表只增不减，第四十轮的输入里堆着前三十九轮的全部内容。

本章讲这堆内容是怎么把任务带偏的，以及怎么管。

## 掰开：消息列表是怎么涨起来的

先看量。假设系统提示词加工具清单 2,000 token，每一轮新增的内容是：模型输出 300，工具结果 3,000（一次检索或一段日志）。

| 轮次 | 这一轮的输入 token | 其中工具结果占 |
|---|---|---|
| 第 1 轮 | 2,000 | 0 |
| 第 10 轮 | 2,000 + 9 × 3,300 = 31,700 | 27,000 |
| 第 40 轮 | 2,000 + 39 × 3,300 = 130,700 | 117,000 |

第 40 轮时，输入里九成是工具结果，其中绝大部分是三十轮以前的旧结果，早已用过。以 128,000 的窗口为例，此时已经装不下了。

## 掰开：四种跑偏

窗口撑爆只是最显眼的一种。更常见的是窗口还没满，质量已经在下降：

| 类型 | 发生了什么 | 表现 |
|---|---|---|
| 溢出 | 内容超过窗口上限 | 请求直接失败，或者最早的内容被截掉，连同用户的原始要求 |
| 稀释 | 有用信息被大量无关内容包围 | 忽略早先的约束，漏掉已经得到的关键发现 |
| 污染 | 早先的错误信息留在上下文里，被后续步骤当作事实 | 一个读错的数被反复引用，结论建立在它上面 |
| 冲突 | 新旧信息并存，互相矛盾 | 一会儿用旧值，一会儿用新值 |

"稀释"有研究支持：输入越长，模型准确取用其中某一条信息的能力越低，这个现象有时被称为上下文腐化。它是渐进的，没有明确的临界点，所以比溢出更难察觉。

结论是：**上下文是有限资源，要像管理内存一样管理它。每放进去一段内容，都在消耗模型的注意力。**

## 五种管理手段

### 一、从源头控制：工具少返回

最便宜的办法是让进入上下文的内容本来就少。

- 检索工具返回最相关的 3 块，而不是 20 块；
- 查日志的工具支持按时间和关键词过滤，而不是返回整个文件；
- 返回结构化的要点，而不是原始的大段文本；
- 超长的结果截断，并注明"已截断，共 N 条，可用某参数查看其余"。

这是第 13 章"工具返回值是给模型看的"在长任务里的延伸。

### 二、清理旧的工具结果

工具结果通常只在紧接着的一两轮里有用。可以把较早的工具结果替换成一个简短的占位说明，保留"调用过什么"的记录，去掉大段的返回内容。

手算效果。沿用上面的数，在第 40 轮时只保留最近 5 轮的完整工具结果，更早的 34 条每条替换为 50 token 的占位说明：

- 模型输出：39 × 300 = 11,700
- 最近 5 轮工具结果：5 × 3,000 = 15,000
- 更早 34 条的占位：34 × 50 = 1,700
- 固定部分：2,000
- **合计 30,400**，原来是 130,700

降到不足四分之一，而模型仍然知道自己做过哪些事。

### 三、压缩：把历史换成摘要

接近窗口上限时，让模型把到目前为止的对话写成一份摘要，然后用摘要替换掉原来的历史，在此基础上继续。

摘要要保留的内容：

| 必须保留 | 可以丢弃 |
|---|---|
| 用户的原始目标和约束 | 工具调用的原始返回 |
| 已经确认的关键发现和数据 | 走不通的尝试的细节 |
| 做过的决定及其理由 | 寒暄和重复内容 |
| 尚未完成的事项 | 已被后续结果取代的中间结论 |

压缩是有损的。摘要漏掉的细节就永远丢了，摘要写错的地方会成为之后的"事实"。所以它是不得已的手段，应该在前两种手段用尽之后才触发。

### 四、外部笔记：把状态写到窗口外面

让 Agent 把重要的东西主动写进一个文件或数据库，需要时再读回来。常见的两种：

- **待办清单**：第 18 章的计划。每完成一步更新一次。它让目标和进度不依赖上下文是否还保留着早先的对话。
- **笔记**：已确认的发现、关键数据。压缩之后，可以从笔记里把要紧的内容重新读回上下文。

这实际上是第 10 章的记忆机制用在了单个长任务内部。

### 五、子 Agent：把脏活隔离出去

有些子任务需要读大量内容，但最后只需要一个简短的结论。例如"读完这 10 份维修记录，告诉我有没有提到电池问题"。

把它交给一个子 Agent：子 Agent 在自己独立的上下文里读完 10 份记录，只把一段结论返回给主 Agent。那 10 份记录从未进入主 Agent 的上下文。第 22 章展开这种做法。

## 还有一个原则：按需加载

与其事先把可能用到的资料都放进上下文，不如只放"目录"，让模型需要时再用工具去取。

| | 预先全放 | 按需加载 |
|---|---|---|
| 上下文里放什么 | 文件的完整内容 | 文件名、路径、一句话说明 |
| 模型需要细节时 | 已经在上下文里 | 调用工具读取 |
| 起始成本 | 高 | 低 |
| 多一次往返 | 否 | 是 |

第 20 章把检索做成工具，是同一个原则。资料小而稳定时预先放入（第 9 章 CAG），资料大或大部分用不上时按需取。

## 缓存与管理的矛盾

第 9 章说过，提示缓存要求前缀逐字相同才命中。上下文管理的每一种手段都在改动历史，一改，从改动处往后的缓存就失效。

所以清理和压缩不能太频繁。合理的做法是设一个阈值，比如用到窗口的七八成时触发一次，一次清理掉足够多的内容，而不是每一轮都改一点。

## 为什么这样设计

第 2 章讲过，上下文完全由程序拼装，这是代价也是权力。长任务里这份权力必须行使：模型只能看到你让它看到的内容，让它看到什么、不看到什么，是 Agent 设计里最直接影响质量的决定。

## 优势、劣势、什么时候不该用

**优势**：让任务可以远超单个窗口的长度；降低每一轮的费用；减少跑偏。

**劣势**：
- 所有手段都有损，可能删掉后面恰好需要的内容；
- 增加了系统的复杂度，出问题时要多考虑一种可能：模型是不是没看到某段内容；
- 与提示缓存有冲突。

**不该用的时候**：任务本身就短，十轮以内、内容不多。这时原样保留全部历史是最好的，任何清理都是多余的风险。

## 常见误解

**"窗口够大就不需要管理。"** 稀释、污染、冲突都发生在窗口没满的时候。窗口大只是推迟了溢出，而且每一轮的费用随长度线性增长。

**"保留的历史越全，模型越了解情况。"** 超过某个量之后，更多的历史让模型更难找到要紧的那几条。

**"压缩之后模型还记得细节。"** 它只知道摘要里写了的内容。

**"这是 Agent 才有的问题。"** 长对话的聊天助手同样如此，只是 Agent 因为工具结果体积大，涨得快得多。

## 小结

- 长任务跑偏的原因在输入：消息列表只增不减，带来溢出、稀释、污染、冲突四类问题，后三类在窗口没满时就会发生。
- 管理手段按优先顺序：工具少返回、清理旧工具结果、外部笔记、子 Agent 隔离，最后才是压缩历史。
