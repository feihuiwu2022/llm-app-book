# 30 命令行与无头模式：Agent 的接口形态

## 从一个问题开场

2025 年前后最受开发者欢迎的几个编程 Agent，主界面是一个黑底的终端窗口。在图形界面已经普及了几十年之后，这看起来像是倒退。

为什么是命令行？

答案和怀旧无关。命令行恰好同时满足了 Agent 对接口的三个要求：模型能读懂、能组合、能脱离人运行。本章讲这三点，以及由此带来的"无头模式"：没有界面、没有人在场的 Agent。

## 掰开：shell 是最通用的工具

第 13 章给车载助手写了三个工具，每个工具做一件事。按这个思路给编程 Agent 配工具，需要：读文件、写文件、搜索、运行测试、查看提交历史、安装依赖、启动服务、查看日志……一百个也列不完。

命令行 Agent 的做法是给一个工具：**执行 shell 命令**。

| | 一百个专用工具 | 一个 shell 工具 |
|---|---|---|
| 工具清单占用 | 100 × 300 = 30,000 token，每轮都带 | 几百 token |
| 覆盖范围 | 只有事先定义的 | 系统上装了的任何程序 |
| 新需求 | 写新工具、改清单 | 模型自己写一条命令 |
| 模型是否熟悉 | 要靠工具说明现学 | 训练数据里有海量的命令行用法 |

最后一行是关键。模型在训练中读过大量的 shell 脚本、命令手册和技术问答，`grep`、`git`、`curl` 怎么用，它本来就知道，不需要在工具说明里教。**命令行是一个模型已经学会的、现成的工具生态。**

这是第 15 章代码执行的延伸：与其逐个定义工具，不如给一个通用的执行环境。

组合性也是现成的。管道把一个程序的输出接到另一个的输入：

```bash
git log --since="1 week ago" --oneline | grep -i fix | wc -l
```

一行命令完成"查最近一周的提交、筛出修复类、计数"三步，只需一次工具调用，中间结果不经过上下文。换成三个专用工具，要三次往返，每次的结果都要进上下文。

实际的 harness 通常是混合的：保留少数几个高频的专用工具（读文件、改文件、搜索），因为专用工具的输入输出更规整、更容易做权限控制和检查点；其余的全部交给 shell。

### 代价：最强的工具也最危险

shell 能做任何事，包括删除整个目录、把文件传到外网、修改系统配置。给模型一个 shell，等于把第 34 章说的"破坏力"开到最大。所以命令行 Agent 的权限设计几乎都围绕这一个工具展开：

- 命令的允许清单和拒绝清单，例如允许 `git diff`，拒绝 `git push`；
- 执行前的人工确认；
- 文件系统和网络的沙箱隔离（第 15 章）；
- 执行前钩子做模式匹配拦截（第 29 章）。

## 掰开：文件是共享的状态

命令行 Agent 的另一个特点是把状态放在文件里：

| 状态 | 放在哪 |
|---|---|
| 工作成果 | 项目里的文件 |
| 项目知识 | 记忆文件（第 24 章） |
| 做事方法 | 技能文件（第 29 章） |
| 配置和规则 | 设置文件 |
| 历史 | 版本管理系统 |

这些文件，人用编辑器能看能改，Agent 用工具也能看能改，两边面对的是同一份东西。没有"Agent 内部状态"和"人看到的状态"之间的同步问题。

版本管理系统因此成了天然的安全网：Agent 的每一处改动都以差异的形式呈现，人可以逐行审阅，不满意可以整体回退。第 31 章的检查点是会话内的快速撤销，版本管理是持久的记录，两者配合。

## 掰开：无头模式

前面讲的都是人坐在终端前和 Agent 对话。无头模式去掉了这个前提：一条命令启动，Agent 跑完，输出结果，退出。没有交互界面。

以 Claude Code 为例，加一个 `-p` 参数就是无头运行：

```bash
claude -p "Find and fix the bug in auth.py" --allowedTools "Read,Edit,Bash"
```

它可以像任何命令行程序一样接进管道，读标准输入，写标准输出：

```bash
cat build-error.txt | claude -p 'concisely explain the root cause of this build error' > output.txt
```

这一步的意义是：**Agent 变成了一个可以被别的程序调用的普通程序。** 于是它能出现在所有程序能出现的地方：

| 场景 | 做法 |
|---|---|
| 持续集成 | 代码提交后自动运行，审查改动或修复失败的检查 |
| 定时任务 | 每天早上汇总昨天的告警 |
| 批处理 | 对一千个文件逐个执行同一项迁移 |
| 被别的系统调用 | 工单系统收到工单后触发一次分析 |
| 被别的 Agent 调用 | 第 26 章的子 Agent，第 27 章的执行层 |

### 无头运行要解决的三件事

没有人在场，原本由人顺手处理的三件事必须事先安排好。

**一、输出要给程序读。** 交互模式下输出是给人看的文字。无头模式下，下游是程序，需要结构化的输出。Claude Code 用 `--output-format json` 返回一个 JSON，里面有结果、会话编号、本次费用等字段；还可以给一份 JSON Schema，让最终结果符合指定结构，这是第 15 章的结构化输出用在了 Agent 的出口上。

**二、权限要事先定好。** 没有人来点"同意"。所以要在启动时声明这次运行允许什么：

- 明确列出允许的工具和命令模式，例如只允许 `Bash(git diff *)`；
- 选一个不会停下来等人的权限模式：凡是需要询问的操作一律拒绝，而不是卡住。

原则是无头运行的权限应该比交互运行更窄，因为没有人盯着。放开一切权限的选项只应该在隔离的容器里使用。

**三、要能接着上次继续。** 一次无头运行结束后，会话被保存下来。下一次可以用会话编号恢复，带着之前的全部上下文继续：

```bash
session_id=$(claude -p "Start a review" --output-format json | jq -r '.session_id')
claude -p "Continue that review" --resume "$session_id"
```

这让多步的自动化流程成为可能：第一步分析，程序根据分析结果做些别的事，第二步回到同一个会话继续。

### 手算：批处理的账

要把 500 个旧接口文件迁移到新写法，每个文件跑一次无头 Agent。假设每次平均 6 轮，固定前缀 5,000 token，每轮新增 2,000，每轮输出 400。套第 35 章的公式，单个文件：

- 累计输入 = 6 × 5,000 + 2,000 × 6 × 5 ÷ 2 = 30,000 + 30,000 = 60,000 token
- 输出 = 6 × 400 = 2,400 token
- 费用（假设单价，不开缓存）= (60,000 × 10 + 2,400 × 40) ÷ 1,000,000 ≈ **0.70 元**

500 个文件约 350 元。每个文件串行耗时约 6 × (0.8 + 400 ÷ 50) ≈ 53 秒，全部串行要 7 个多小时，10 路并行约 44 分钟。

批处理有两条经验：

- **先拿三五个文件试跑**，把提示词调到满意，再放开跑全部。500 次运行里发现提示词有问题，代价是 500 倍。
- **每个文件一个独立会话。** 互不干扰，某一个失败了只需重跑那一个，也不会出现第 23 章的上下文堆积。

## 接口形态的选择

命令行不是唯一的形态，各有适用：

| 形态 | 适合 | 局限 |
|---|---|---|
| 交互式命令行 | 开发者；任务需要来回讨论 | 非技术用户有门槛 |
| 编辑器或桌面应用 | 需要看差异、看图、点选 | 难以自动化 |
| 无头命令 | 自动化、批处理、被程序调用 | 没有中途纠正的机会 |
| 程序库（SDK） | 嵌进自己的产品 | 要自己做界面和周边 |
| 聊天工具里的机器人 | 团队协作；第 27 章的常驻 Agent | 输出受消息格式限制 |

一个设计良好的 harness 应该是同一个核心、多种入口（第 28 章）。这样在交互模式下调好的技能、钩子、权限规则，可以原样用到无头模式里。

车载助手的接口形态是语音，但后台同样有无头的部分：夜间批量分析车辆日志、定时检查保养到期，都是没有人在场的运行。

## 为什么这样设计

Unix 的设计哲学是让每个程序做好一件事，并通过文本流互相组合。命令行 Agent 把自己做成了这个生态里的一员：它调用别的程序（shell 工具），也被别的程序调用（无头模式）。文本恰好又是 LLM 的母语，两者之间不需要任何适配层。

## 优势、劣势、什么时候不该用

**优势**：一个 shell 工具覆盖海量能力；状态都是文件，人和 Agent 共享；无头模式让 Agent 可以被编排进任何自动化流程。

**劣势**：
- shell 的破坏力大，权限和隔离必须做好；
- 命令的输出是给人看的自由文本，冗长的输出会淹没上下文，需要截断和过滤（第 23 章）；
- 无头运行出错时没有人当场纠正，要靠日志事后排查（第 33 章）。

**不该用的时候**：
- 面向普通消费者的产品，命令行不是合适的交互方式；
- 运行环境无法隔离，又必须给 shell 权限；
- 任务需要频繁的人工判断，硬做成无头只会产出一堆要返工的结果。

## 常见误解

**"命令行 Agent 只是没来得及做图形界面。"** 命令行是有意的选择：工具生态现成、可组合、可自动化。图形界面是在这个核心之上加的另一个入口。

**"无头模式就是把确认全部关掉。"** 正相反，它要求事先把允许的范围写清楚，范围之外的一律拒绝。

**"给了 shell 就不需要别的工具了。"** 读写文件这类高频操作用专用工具更稳定，也更容易做检查点和权限控制。

**"无头运行的结果可以直接用。"** 它没有经过人的中途纠正。输出应该进入某种审核环节：一个合并请求、一份待确认的报告。

## 小结

- 命令行适合做 Agent 的接口，是因为 shell 是模型已经学会的通用工具，一个工具覆盖一个生态，并且天然可组合。
- 状态放在文件和版本管理里，人和 Agent 面对同一份东西，改动可审阅、可回退。
- 无头模式让 Agent 成为可被程序调用的程序；没有人在场，所以输出要结构化、权限要事先收窄、会话要能恢复。
