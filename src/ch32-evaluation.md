# 32 评测：怎么知道改好了还是改坏了

## 从一个问题开场

你把 RAG 的块大小从 400 改成 300，试了五个问题，感觉答得更好了，于是上线。一周后用户投诉变多。

哪里出了问题？试的那五个问题变好了，另外五十个你没试的变坏了。

前面每一章都在说"用自己的问题集实测"。本章讲这个"实测"到底怎么做。没有评测，前面二十二章的所有调整都是凭感觉。

## 掰开：一套评测的三样东西

| 组成 | 是什么 | 实物形态 |
|---|---|---|
| 测试集 | 一批有代表性的输入，以及每个输入的期望结果 | 一个表格或 JSON 文件 |
| 判分器 | 判断一次输出合不合格的方法 | 一段程序，或一段给模型的评分提示词 |
| 指标 | 把所有判分结果汇总成的数字 | 正确率、召回率等 |

测试集里一条记录的样子：

```json
{
  "问题": "胎压报警灯亮了是低于多少？",
  "期望答案要点": ["190千帕"],
  "答案所在的块": [1],
  "类型": "事实查询"
}
```

这就是第 3 章探针的扩展版：题目从 4 道变成几十上百道，并且固定下来，每次改动后重跑。

## 测试集从哪来

| 来源 | 做法 | 特点 |
|---|---|---|
| 真实用户问题 | 从线上日志抽样 | 最有代表性，是首选 |
| 失败案例 | 每个线上错例都加进测试集 | 防止同一个问题再次出现 |
| 人工编写 | 业务专家按场景写 | 能覆盖日志里还没出现的情况 |
| 模型生成 | 让模型读文档出题 | 快，但偏简单、偏书面，要人工筛 |

要有意识地覆盖几类：

- 常见问题；
- 边界情况：资料里没有答案的问题（期望结果是拒答）、有歧义的问题；
- 第 7、8 章提过的难题：答案分散在多处的、需要计算的。

**起步不需要多。** 30 到 50 条认真挑选的题目，就足以发现大部分明显的问题。先有，再逐步加。

## 判分器的三种做法

### 一、程序判分

能用代码判的，优先用代码：

| 检查什么 | 怎么判 |
|---|---|
| 分类结果 | 和标准答案是否相等 |
| 答案包含关键事实 | 是否包含"190" |
| 格式 | 能否被解析、字段是否齐全 |
| 检索 | 正确的块是否在取回的结果里 |
| Agent 的动作 | 任务结束后，真实状态是否符合预期 |

快、便宜、每次结果一致。缺点是只能判断有明确对错标准的情况。

### 二、模型判分

开放性的回答（一段解释、一份总结）没法用字符串匹配。可以让另一次模型调用来打分：

```text
下面是一个问题、参考答案和待评答案。
请判断待评答案是否包含参考答案中的全部要点，且没有与参考答案矛盾的内容。
先写出分析，再在最后一行只输出"合格"或"不合格"。
```

要点：

- 评分标准要具体。"回答质量如何"得不到稳定的分数；"是否包含以下三个要点"可以。
- 让它先分析再给结论，这是第 18 章的思维链。
- 用"合格 / 不合格"或很少的几档，不用 1 到 10 分。分档越细越不稳定。
- **判分器本身要校准**：人工标 50 条，对比模型判分与人工判分的一致率。一致率不高，就改评分提示词，直到可用。

### 三、人工判分

最准，最贵，最慢。用于校准模型判分器，以及定期抽检。

## 分环节的指标

第 7 章说过，RAG 要分环节测。每个环节有自己的指标。

### 检索指标：手算一次

三个问题，各自的正确块在检索结果里排第几：

| 问题 | 正确块的名次 | 是否在前 5 | 名次的倒数 |
|---|---|---|---|
| 问题 1 | 第 1 | 是 | 1 |
| 问题 2 | 第 3 | 是 | 1/3 ≈ 0.333 |
| 问题 3 | 没找到 | 否 | 0 |

- **前 5 召回率**（Recall@5）= 2 ÷ 3 ≈ **0.67**。含义：有多大比例的问题，正确的块进了前 5。
- **平均倒数排名**（MRR）= (1 + 0.333 + 0) ÷ 3 ≈ **0.44**。含义：正确的块平均排得多靠前，越接近 1 越好。

召回率回答"找没找到"，MRR 回答"排得好不好"。加重排模型主要提升的是后者。

### 生成指标

常用的两个：

- **忠实度**：答案里的每一个论断，是否都能在给它的资料里找到依据。测的是有没有编造。
- **答案正确性**：答案是否与参考答案一致。

两者要分开看。一个回答可以完全忠实于资料但答非所问，也可以碰巧答对但其实没有依据。

### Agent 的评测

Agent 每次走的路径可能不同，但都能完成任务。所以评测要点是：

- **判结果，不判路径。** 检查最终状态：空调是不是 22 度、工单是不是建对了。不要要求它必须按某个顺序调用某些工具。
- **同一题跑多次。** Agent 的波动比单次调用大，一次成功不代表稳定。
- **同时记录成本。** 轮数、token、耗时都是指标。完成率相同时，轮数少的方案更好。

## 手算一次：多少条才够下结论

测试集 50 条，改动前正确率 80%，改动后 84%。改好了吗？

正确率是抽样估计，有误差。标准误差的近似公式：

**标准误差 = √( p × (1 − p) ÷ n )**

其中 p 是正确率，n 是题目数。95% 置信区间约为正负 1.96 倍标准误差。

| 题目数 | 正确率 80% 时的标准误差 | 95% 区间 |
|---|---|---|
| 50 | √(0.8 × 0.2 ÷ 50) ≈ 0.057 | 80% ± 11% |
| 100 | 0.040 | 80% ± 8% |
| 400 | 0.020 | 80% ± 4% |

50 条的测试集上，正确率的不确定范围是正负 11 个百分点。80% 到 84% 的变化完全在噪声之内，不能下结论。

想要分辨 4 个百分点的差异，大约需要 400 条。误差与题目数的平方根成反比：**精度提高一倍，题目数要变成四倍。**

小测试集仍然有用，它能发现大的变化（从 60% 到 85%）和具体的错例。只是不要拿它分辨细微差别。另一个办法是逐题对比改动前后的结果：两个版本在哪些题上答案不同，直接看这些题，比只看总分更有信息量。

## 把评测接进流程

| 时机 | 做什么 |
|---|---|
| 每次改提示词、换参数、换模型 | 跑完整测试集，和上一版逐题对比 |
| 上线前 | 正确率不低于基线；关键用例全部通过 |
| 上线后 | 持续从日志抽样，人工或模型判分，监控趋势 |
| 发现线上错例 | 加入测试集 |

最后一行形成一个闭环：测试集随时间越来越贴近真实使用。

## 为什么这样设计

模型的输出是概率性的，系统的环节又多，任何改动的影响都无法靠推理预知，只能测。固定的测试集把"感觉变好了"变成一个可以重复、可以比较的数字，这是所有后续优化的前提。

## 优势、劣势、什么时候不该用

**优势**：改动有依据；能防止修好一处搞坏另一处；换模型时能快速判断新模型是否可用。

**劣势**：建测试集要投入业务专家的时间；测试集会过时，要持续维护；模型判分器自己也会出错。

**不该做的事**：对着测试集反复调，直到分数很高。这会让系统只在这批题上好。留一部分题目平时不看，只在最终验收时使用。

## 常见误解

**"先把系统做出来，评测以后再补。"** 没有评测时做的每个决定都无法验证。先花一天建 30 条测试集，后面每一步都更快。

**"公开榜单上分数高的模型，在我的任务上也好。"** 榜单测的是通用能力。你的任务、你的数据、你的格式要求，只有你自己的测试集能测。

**"模型判分不可靠，所以不能用。"** 未经校准的不可靠。和人工标注对过、一致率达标的，可以大规模使用。

**"正确率从 80% 涨到 83%，说明改动有效。"** 先算误差范围。

## 小结

- 评测由测试集、判分器、指标三样组成；测试集优先取自真实问题和失败案例，30 到 50 条即可起步。
- 判分优先用程序，开放性回答用校准过的模型判分；RAG 分环节测，Agent 判结果不判路径。
- 正确率有抽样误差，50 条时约正负 11 个百分点，小的分数差异不能当作结论。
