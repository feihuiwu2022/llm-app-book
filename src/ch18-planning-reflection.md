# 18 规划与反思

## 从一个问题开场

把任务换成一个大的："为新车型的空调系统写一套测试用例，覆盖手册里提到的全部功能。"

用第 17 章的 ReAct 去做，容易出现两种情况：

- **走着走着忘了目标。** 每一轮只决定眼前这一步，做到第十五轮时还在反复查某个细节，全部功能只覆盖了三分之一。
- **做错了不知道。** 写出的用例里把温度上限写成了 30 度，手册上是 32 度。没有任何一步回头检查。

ReAct 是走一步看一步。它缺两样东西：出发前的路线图，和交卷前的检查。这就是规划与反思。

## 手算一次：为什么长任务容易失败

假设每一步做对的概率是 95%，各步独立，任何一步错了整个任务就错：

| 步数 | 全部做对的概率 | 计算 |
|---|---|---|
| 5 | 77% | 0.95⁵ |
| 10 | 60% | 0.95¹⁰ |
| 20 | 36% | 0.95²⁰ |

单步 95% 听起来很高，二十步的任务成功率却只有三分之一。把单步正确率提到 99%，二十步是 0.99²⁰ ≈ 82%。

这个算式指出了两条出路：

- **减少要连续做对的步数**：把大任务拆成几段，每段单独验收。这是规划。
- **让错误可以被发现并改正**：不要求每步都对，只要求错了能改回来。这是反思。

## 掰开：规划

规划是在动手之前，先让模型把任务拆成若干步，写成一份清单：

```text
任务：为空调系统写测试用例，覆盖手册里的全部功能

计划：
1. 检索手册，列出空调系统的全部功能点
2. 对每个功能点，确定正常值、边界值、异常输入
3. 逐个功能点编写用例
4. 对照第 1 步的清单检查覆盖情况
```

这份清单的实物形态就是一段文字，放在上下文里，或者存成一个外部的待办列表。执行时每完成一步，标记一步。

它起三个作用：

| 作用 | 说明 |
|---|---|
| 锚定目标 | 清单一直在上下文里，每一轮都能看到"总共要做什么、做到哪了" |
| 分段验收 | 每一步有明确产出，可以单独检查 |
| 让人介入 | 计划可以先给人过目，方向错了在动手前就能纠正，成本最低 |

### 两种节奏

| | 先规划后执行 | 边执行边调整 |
|---|---|---|
| 做法 | 一次性列出完整计划，然后照做 | 列出计划，每做完一步，根据结果修订后面的步骤 |
| 优点 | 可预测，执行阶段可以用便宜的模型 | 能应对意外 |
| 缺点 | 计划基于的假设错了就全错 | 调用次数多，可能反复改计划而不推进 |
| 适合 | 步骤清晰、意外少的任务 | 探索性任务，例如排查故障原因 |

实际系统多用后一种：有一份计划，但允许修订。

还有一类更重的做法是同时展开多条路线，分别评估后选择最有希望的继续，走不通再回退。它适合搜索空间明确、对错容易判断的问题，成本是调用量成倍增加，一般业务场景很少用得上。

## 掰开：反思

反思是让模型回头检查已经做出的结果，找出问题，再改。

最简单的形式是两次调用：

1. **生成**：写出测试用例。
2. **检查**：把用例和手册原文一起交给模型，问"逐条核对，用例里的数值与手册是否一致？列出不一致的地方"。
3. **修改**：根据检查意见重写。

### 反思有效的前提：要有外部依据

让模型空对着自己的输出问"你确定吗"，效果有限。它要么坚持原来的错误，要么把原本对的改成错的。**反思需要新的信息才有意义。**

| 反思的依据 | 可靠程度 | 例子 |
|---|---|---|
| 程序给出的客观结果 | 高 | 代码运行报错、测试没通过、JSON 校验失败 |
| 原始资料 | 较高 | 把答案和手册原文逐条对照 |
| 另一次独立的模型调用，按明确标准检查 | 中 | 给一份检查清单：是否覆盖边界值、是否有预期结果 |
| 模型凭感觉自查 | 低 | "再检查一遍" |

能用程序验证的，就不要用模型判断。写代码的任务之所以特别适合 Agent，就是因为有编译器和测试这种客观的反馈来源。

### 把教训留给下一次

反思的结果还可以保存下来。一次任务失败后，让模型总结"哪里做错了、下次应该怎样"，把这段总结存进第 10 章的长期记忆，下次遇到同类任务时取出来放进上下文。模型的权重没有变，但同样的错误不会再犯第二次。

## 资源账本

以"生成、检查、修改"为例，假设生成一次是输入 3,000、输出 1,500：

| 调用 | 输入 | 输出 |
|---|---|---|
| 生成 | 3,000 | 1,500 |
| 检查（读入用例和手册） | 3,000 + 1,500 = 4,500 | 300 |
| 修改（读入用例、手册、意见） | 4,500 + 300 = 4,800 | 1,500 |
| **合计** | **12,300** | **3,300** |

对比只生成一次的 3,000 和 1,500：输入约 4 倍，输出约 2.2 倍，耗时约 3 倍。如果检查不通过再来一轮，继续累加。所以反思的轮数必须设上限，通常一到两轮。

## 为什么这样设计

规划和反思对应人做复杂事情的两个习惯：动手前列提纲，交卷前检查。它们存在的原因是同一个：单步生成会出错，长链条会放大错误。规划缩短每一段链条，反思给错误一个被纠正的机会。

## 优势、劣势、什么时候不该用

**优势**：提高长任务的完成率和结果质量；计划和检查意见都是可读的文字，人可以介入。

**劣势**：调用次数成倍增加；规划可能流于形式，写出一份四平八稳但没用的清单；没有外部依据的反思可能越改越差。

**不该用的时候**：
- 任务只有两三步，规划的开销大于收益；
- 没有任何可供核对的依据，反思只能是模型自说自话；
- 对延迟敏感的交互场景。

## 常见误解

**"让模型多检查几遍就更准。"** 没有新信息的重复检查，收益很快归零，还可能把对的改错。

**"计划越详细越好。"** 过细的计划在第一个意外出现时就作废了。计划写到"每一步的产出是什么"即可，怎么做留给执行时决定。

**"用了推理模型就不需要显式规划。"** 推理模型的内置思考适合单次调用内的规划。跨越几十轮的长任务仍然需要一份留在上下文里或存在外部的计划，因为早先的思考内容不一定会一直保留。

**"反思是让同一个模型扮演批评者。"** 可以是同一个模型，但要换提示词、给检查标准、给依据。更可靠的是不用模型，直接跑测试。

## 小结

- 长任务的成功率是各步正确率的连乘，规划通过分段缩短链条，反思通过纠错提高每段的正确率。
- 规划的产物是一份留在上下文里的清单，作用是锚定目标、分段验收、让人提前介入。
- 反思要有外部依据：程序反馈最好，原始资料次之，凭感觉自查最差；轮数要设上限。
