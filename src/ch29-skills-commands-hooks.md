# 29 扩展机制：技能、命令、钩子

> ▶ 本章配套代码：`code/ch29_extend.py` 和 `code/skills/`，只用 Python 标准库，可直接运行。

## 从一个问题开场

车载助手上线后，需求不断加进来：

- 长途出行前有一套固定的检查流程，希望助手每次都按这个流程走；
- 客服想输入一个简短的口令，就触发一段写好的标准任务；
- 安全团队要求：某些操作在任何情况下都必须先记录、不许直接执行。

三个需求都是"给 Agent 加东西"，但性质完全不同。第一个是教它一套做法，第二个是给人一个快捷入口，第三个是一条不容商量的规则。

把它们都写进系统提示词是最直接的做法，也是最差的：提示词越来越长，每轮都要付费，而第三条写在提示词里根本不算"必须"。

成熟的 harness 为这三类需求提供了三种不同的扩展机制。本章以 Claude Code 的设计为主要实例来讲，这三种机制在其他 harness 里有各自的名字，结构相通。

## 主线：谁触发

三种机制的根本区别在于由谁决定它何时生效：

| 机制 | 谁触发 | 性质 | 回答的问题 |
|---|---|---|---|
| 技能 | 模型 | 概率性：模型判断用得上才用 | 这类任务该怎么做 |
| 命令 | 用户 | 显式：用户输入才触发 | 我想让它现在做这件事 |
| 钩子 | 事件 | 确定性：到了那个时刻必然执行 | 这件事无论如何都要发生 |

加上第 13 章的工具（也是模型触发），一共四样。遇到一个新的扩展需求，先问"应该由谁来决定它什么时候发生"，就知道该用哪一种。

## 掰开：技能

### 实物形态

一个技能是一个文件夹，里面有一个说明文件，可以附带脚本和参考资料。配套代码里的 `code/skills/long-trip/SKILL.md`：

```markdown
---
name: long-trip
description: 长途出行前的车辆检查流程。用户提到长途、自驾、跑高速、出远门时使用。
---
# 长途出行前检查

按顺序做完下面三步，再给用户一份汇总。

1. 调用 get_tire_pressure 读取四个轮胎的胎压。
2. 调用 search_manual 查"胎压标准值"，逐个轮胎与标准对比；任何一个低于报警线都要明确提醒，不要只报平均值。
3. 调用 set_ac_temperature 把空调预设为 22 度。
……
```

两段 `---` 之间是头部，写名字和描述；下面是正文，写具体做法。它就是一份给模型看的操作手册。

### 关键设计：分三层加载

| 层 | 内容 | 什么时候进上下文 |
|---|---|---|
| 第一层 | 每个技能的名字和描述 | 始终在 |
| 第二层 | 说明文件的正文 | 模型判断用得上、调用它的时候 |
| 第三层 | 附带的参考资料、脚本 | 正文里提到、并且确实需要的时候；脚本是被执行，不是被读入 |

这叫渐进式披露。配套代码的输出显示了第一层的样子：

```text
技能清单（常驻上下文，92 字符；全部正文预载要 517 字符）：
- long-trip：长途出行前的车辆检查流程。用户提到长途、自驾、跑高速、出远门时使用。
- tire-check：胎压异常时的排查流程。用户说胎压报警、轮胎瘪了、警告灯亮时使用。
```

两个技能时差别不大。放大到实际规模手算：50 个技能，每个描述 100 token，正文 3,000 token。

| | 常驻上下文 |
|---|---|
| 全部正文写进系统提示词 | 50 × 3,000 = 150,000 token |
| 只放描述，按需加载 | 50 × 100 = 5,000 token |

相差 30 倍。一次任务通常只用到一两个技能，按需加载后实际进入上下文的是 5,000 加上一两份正文。**技能让"会的东西很多"和"每轮带的东西很少"可以同时成立。**

这回答了第 14 章留下的问题。MCP 工具的说明是全部常驻的，接得越多前缀越长。技能把同样的思路反过来：先给目录，要用再翻到那一页。

Claude Code 对这三层有具体的约束：描述在清单里超过一千五百多个字符会被截断；整个清单的预算默认是上下文窗口的 1%；建议说明文件正文控制在 500 行以内，更细的内容拆到附带文件里。

### 描述决定了技能会不会被用上

模型只凭第一层的描述决定要不要加载。描述写成"车辆检查"，模型不知道什么时候该用。好的描述包含两部分：这个技能做什么，以及**什么情况下该用它**，最好带上用户可能说的词。上面例子里的"用户提到长途、自驾、跑高速、出远门时使用"就是后一部分。

这仍然是概率性的。模型可能该用没用，所以流程性极强、绝不能跳过的要求，不应该只放在技能里。

### 技能和几样相近的东西

| | 存的是什么 | 怎么生效 |
|---|---|---|
| 技能 | 做事的方法 | 按需读入上下文 |
| 工具 | 一个可执行的动作 | 模型发调用请求，程序执行 |
| 记忆文件 | 项目的事实和约定 | 每次会话整份读入 |
| 微调 | 行为习惯 | 烧进权重 |

技能常常是"怎样组合使用几个工具"的说明。和微调相比，它存的同样是做事方法，但放在可以随时编辑、可以进版本管理、可以给人审阅的文件里，改一行立即生效。第 12 章说微调适合需求稳定的场景；需求还在变的做事方法，写成技能更合适。

## 掰开：命令

命令是用户触发的快捷方式：输入一个斜杠加名字，程序把它展开成一段预先写好的提示词。

```text
命令展开：/trip 明天  →  我明天要跑长途，出发前帮我把车检查一遍。
```

配套代码里的实现只有几行，就是字符串模板替换。它的价值不在技术上，而在于把一段反复使用的、经过打磨的任务描述固定下来，团队里每个人触发的都是同一个版本。

命令和技能的内容形态很接近，都是一段给模型的说明。区别只在谁触发。所以在 Claude Code 里两者已经合并：一个技能默认既可以由模型自动调用，也可以由用户用斜杠加名字手动调用，并且可以分别关掉其中一种。只允许用户触发的典型例子是"部署到生产环境"，这种事不应该由模型自己觉得该做就去做。

## 掰开：钩子

钩子是挂在 Agent 生命周期特定节点上的普通程序。到了那个节点，harness 必然运行它，不经过模型的判断。

常见的挂载点：

| 时刻 | 能做什么 | 例子 |
|---|---|---|
| 会话开始 | 注入信息 | 加载当前分支和未完成事项 |
| 用户提交输入时 | 检查或补充输入 | 拦截包含密钥的输入 |
| 工具执行前 | 放行、拦截、改写参数 | 禁止修改某个目录；危险命令一律拒绝 |
| 工具执行后 | 追加处理 | 改完代码自动跑格式化和检查 |
| Agent 准备结束时 | 检查是否真的做完 | 测试没通过就不许结束，让它继续 |

在 Claude Code 里，这些节点分别叫 `SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PostToolUse`、`Stop`，另有二十多种覆盖子 Agent、压缩、权限请求等时刻。最常见的钩子形态是一条 shell 命令：harness 把事件详情（工具名、参数等）以 JSON 形式从标准输入传给它，它用退出码回话，退出码 2 表示拦截，并把错误输出作为原因反馈给模型。配置长这样：

```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [ { "type": "command", "command": ".claude/hooks/no-rm.sh" } ] }
    ]
  }
}
```

`matcher` 指定这条钩子只对哪个工具生效。

### 跑一遍：用钩子实现观察模式

配套代码写了一个执行前钩子，规则是只读工具放行，有副作用的工具只记录、不执行。这正是第 27 章常驻 Agent 的"观察档"：

```python
READ_ONLY = {"get_tire_pressure", "search_manual", "load_skill"}

def observe_only(name, arguments):
    if name not in READ_ONLY:
        return f"观察模式：{name} 未执行，已记录供人工确认"
    return None   # None 表示放行
```

同一个任务、同一个模型，挂与不挂这个钩子各跑一遍：

```text
观察模式（挂上执行前钩子）
  第 1 轮  load_skill  →  已执行
  第 2 轮  get_tire_pressure  →  已执行
  第 2 轮  search_manual  →  已执行
  第 3 轮  set_ac_temperature  →  被钩子拦截
  答复：暂时不建议出发。右前185千帕，低于报警线，请先检查补气。空调未调整，等待你确认后再设置。出发前建议充电至百分之一百。
  空调真实状态：24 度；审计记录 4 条

正常模式（不挂执行前钩子）
  ……
  第 3 轮  set_ac_temperature  →  已执行
  答复：暂时不建议出发。右前185千帕，低于报警线，请先检查补气。空调已预设为22度。出发前建议充电至百分之一百。
  空调真实状态：22 度；审计记录 4 条
```

这一段输出里三种机制都出现了：

- **命令**：用户输入 `/trip 明天`，被展开成完整任务；
- **技能**：第 1 轮模型根据清单里的描述加载了 `long-trip`，之后几轮照着正文的三步走；
- **钩子**：第 3 轮的 `set_ac_temperature` 被拦下，空调真实状态保持 24 度；执行后钩子留下了 4 条审计记录。

还有一个细节：被拦截之后，拒绝原因作为工具结果回到了模型面前，所以模型的答复变成了"空调未调整，等待你确认"。**钩子拦截的是动作，同时要把原因告诉模型**，否则模型会以为动作成功了，或者换个办法再试一次。

### 钩子在主循环里的位置

配套代码在第 21 章的循环上只加了三处：

```python
system = "……可用技能如下……\n" + skill_listing()                       # 扩展点一：技能清单进系统提示词
messages = [..., {"role": "user", "content": expand(user_input)}]         # 扩展点二：展开命令
...
denied = next((r for hook in pre_hooks if (r := hook(name, arguments))), None)   # 扩展点三：执行前钩子
```

第三处正是第 13 章说的"程序执行工具的那一行"之前。第 34 章讲的权限控制、人工确认，在实现上都是这个位置的钩子。

### 钩子的边界

钩子是确定性的，这是优点也是限制。它只能做程序能判断的事："这个命令里有没有 `rm -rf`"可以，"这次修改是否符合架构规范"不行。后一类需要判断的检查，仍然要交给模型，例如在钩子里再发起一次模型调用，那就又回到了概率性。

钩子自己也是以你的权限运行的代码，写错了会拦住一切，或者什么都没拦住。它需要像别的代码一样被测试。

## 打包与分发

技能、命令、钩子，再加上 MCP 服务端配置和子 Agent 定义，可以打成一个包整体分发。Claude Code 称之为插件。意义在于团队沉淀下来的做法可以像代码库一样被安装、升级和共享，而不是每个人各自往配置里粘贴。

顺带一提子 Agent 的定义：它也是一个带头部的说明文件，头部里可以限定这个子 Agent 能用哪些工具。只读的调研型子 Agent 不给写入工具，这是第 26 章"职责分离"的落地方式。

## 为什么这样设计

三种机制对应三种不同的可靠性要求。做事方法允许模型灵活取用，所以交给模型触发，并用按需加载控制成本。人想要的明确动作应该有明确入口，所以交给用户触发。不容违反的规则不能依赖任何概率性判断，所以交给事件触发的代码。

把它们混在一起，全部塞进系统提示词，是把三种要求都降成了"模型大概会照做"。

## 优势、劣势、什么时候不该用

**优势**：
- 能力可以持续增加而不撑大每轮的上下文；
- 规则有了确定性的执行位置；
- 扩展内容是普通文件，可以审阅、版本管理、共享。

**劣势**：
- 技能是否被触发取决于描述质量和模型判断，会漏；
- 钩子多了之后，行为由模型和多段代码共同决定，排查问题更复杂；
- 第三方的技能和插件是别人写的指令和代码，安装它们等于信任它们（第 34 章）。

**不该用的时候**：只有两三条简单规则、一两个工具的小系统。直接写在系统提示词和代码里更清楚。扩展机制是为规模准备的。

## 常见误解

**"技能就是把提示词存成了文件。"** 关键在分层加载。存成文件但每次全部读入，和写在系统提示词里没有区别。

**"重要的规则写进技能就安全了。"** 技能是概率性触发的。必须执行的规则要用钩子。

**"钩子可以替代权限系统。"** 钩子是实现权限控制的一种手段。完整的权限系统还包括模式、规则清单、沙箱（第 31、34 章）。

**"技能越多越好。"** 清单本身也占上下文，描述相近的技能会让模型选错。和工具一样，要定期清理。

## 小结

- 三种扩展机制按"谁触发"区分：技能由模型触发，命令由用户触发，钩子由事件触发；先问该由谁决定，再选机制。
- 技能的核心是三层按需加载，常驻的只有名字和描述；描述要写清做什么和什么时候用。
- 钩子是生命周期节点上必然执行的代码，是"必须发生"的规则的落点；拦截动作的同时要把原因告诉模型。
