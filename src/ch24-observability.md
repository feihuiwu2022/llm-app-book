# 24 可观测与调试

## 从一个问题开场

用户反馈："昨天下午问胎压，助手答了个 230，是错的。"

你想重现这个问题，同样的话问了十遍，全都答对了。

传统软件里，同样的输入得到同样的输出，问题可以重现。LLM 应用不行：输出有随机性，检索结果随资料库变化，对话历史每个人都不同。**事后重现往往做不到，所以必须在事发当时把现场记下来。** 这就是可观测要解决的事。

第 7 章的定位方法有一个前提，"把这一次请求的中间产物调出来"。本章讲这些中间产物怎么记。

## 掰开：一次请求的记录长什么样

一次请求从进入系统到返回答案，经过的每一步都记成一条记录，叫一个跨度（span）。同一次请求的所有跨度串成一棵树，叫一条追踪（trace）。

一次 RAG 问答的追踪：

```text
追踪 trace_7f3a　用户问题：胎压报警灯亮了是低于多少　总耗时 2350 毫秒
├─ 问题嵌入　　　　20 毫秒
├─ 召回　　　　　　35 毫秒　向量 50 块 + 关键词 50 块，融合后 50 块
├─ 重排　　　　　 180 毫秒　50 块 → 5 块
├─ 拼装提示词　　　15 毫秒
└─ LLM 生成　　 2100 毫秒　输入 2100 token，输出 62 token，正常结束
```

五段相加：20 + 35 + 180 + 15 + 2100 = 2350 毫秒。一眼能看出时间花在哪：LLM 生成占了 89%。想提速，优化召回是没用的。

Agent 的追踪是多层的：每一轮是一个跨度，里面嵌着一次模型调用和若干次工具调用。

## 每个跨度要记什么

### 模型调用

| 字段 | 为什么要记 |
|---|---|
| 完整的输入：系统提示词、消息列表、工具清单 | 模型的行为完全由输入决定，没有它就无法分析 |
| 完整的输出，包括工具调用请求 | 看模型实际说了什么 |
| 模型名称和版本、温度等参数 | 模型升级后行为会变 |
| 输入、输出、缓存命中的 token 数 | 算成本 |
| 首字延迟、总耗时 | 算延迟 |
| 结束原因 | 区分正常结束、被截断、被过滤 |
| 提示词模板的版本号 | 知道是哪一版提示词产生的 |

第一行最重要。**记下模型实际收到的完整输入**，不是模板，不是你以为它收到的内容。大量问题的原因是拼出来的提示词和设想的不一样：变量没替换、检索结果为空、历史被截断。

### 检索

查询文本（改写前和改写后）、每一路取回的块编号和分数、融合和重排后的顺序。第 7 章的三个定位问题就是在这些字段上查的。

### 工具调用

工具名、参数、返回值、耗时、是否出错。

### 关联信息

追踪编号、会话编号、时间戳、用户反馈（点赞、点踩、是否重新提问）。用户反馈是最便宜的质量信号，一定要和追踪关联起来。

## 用记录来调试

回到开场的问题。有了追踪，过程是这样的：

1. 按时间和用户找到那条追踪。
2. 看 LLM 那个跨度的输入。按第 7 章的方法搜"190"或"240"。
3. 发现提示词的"资料"部分是空的。
4. 看检索跨度：召回返回了 0 块。
5. 看该跨度的错误字段：向量库连接超时，代码捕获了异常，返回了空列表。

原因找到了：检索失败时，系统没有报错，而是带着空资料去问模型，模型凭印象编了一个数。这是一个第 7 章失败点 1 的变体，由一次基础设施故障触发。

没有追踪，这个问题几乎不可能查出来，因为向量库恢复之后一切正常。

修复有两处：检索失败时应该明确告诉用户"暂时查不到"，而不是静默降级；提示词里的"资料中没有就说未提及"那句退路要生效。

### 重放

因为记下了完整输入，可以把它原样重新发给模型。这有两个用处：

- 改了提示词后，拿历史上的真实输入重跑，看输出怎么变；
- 把出错的那条追踪转成第 23 章测试集里的一条用例。

可观测和评测是连在一起的：追踪提供原料，评测把它固化成回归检查。

## 汇总成指标

单条追踪用于查具体问题，汇总后用于看整体：

| 类别 | 指标 | 用途 |
|---|---|---|
| 质量 | 用户点踩率、拒答率、抽样判分的正确率 | 发现质量下滑 |
| 延迟 | 首字延迟、总耗时的中位数和 95 分位 | 发现变慢 |
| 成本 | 每次请求的 token、每天的总费用 | 发现费用异常 |
| 可靠性 | 模型调用错误率、工具调用错误率、被截断的比例 | 发现故障 |
| Agent 专属 | 每个任务的平均轮数、触及轮数上限的比例 | 发现打转 |

延迟要看分位数，不能只看平均值。假设 100 次请求里，95 次耗时 2 秒，5 次耗时 30 秒：

- 平均值 = (95 × 2 + 5 × 30) ÷ 100 = 3.4 秒，看起来还行
- 95 分位以上是 30 秒，每 20 个用户就有 1 个等了半分钟

平均值把最差的体验抹平了。

## 隐私

追踪里是用户的原话和业务数据。记录它们的同时要做到：

- 敏感字段（手机号、车架号、位置）在写入前脱敏；
- 访问追踪数据要有权限控制和审计；
- 设定保留期限，到期删除；
- 符合所在地区对个人信息的法规要求。

"全部记下来"和"保护隐私"之间的平衡，要在系统设计时就定好，事后补很难。

## 为什么这样设计

LLM 应用的行为由运行时的输入决定，而输入是程序在那一刻动态拼出来的，代码里看不到。追踪把那一刻的实际输入输出保存下来，让"为什么它当时这么答"这个问题有据可查。

## 优势、劣势、什么时候不该用

**优势**：问题可定位；成本和延迟可度量；为评测持续提供真实数据。

**劣势**：
- 存储量大，完整的输入输出比传统日志大得多；
- 隐私和合规负担；
- 需要投入来搭建和查看，记了不看等于没记。

**不该省的时候**：没有不该做的阶段。从第一个原型开始就应该至少把每次模型调用的完整输入输出记到文件里。这是成本最低、回报最高的一项工程投入。

## 常见误解

**"有普通的应用日志就够了。"** 普通日志记的是"调用了模型，耗时 2 秒，成功"。调试需要的是"发了什么，回了什么"。

**"只记出错的请求。"** LLM 应用的错误大多不抛异常。答错了的请求在系统看来是一次成功的调用。

**"记下提示词模板和变量就行。"** 要记拼装之后的最终文本。模板加变量推不出截断、编码、空值造成的差异。

**"看平均延迟就能知道用户体验。"** 看 95 分位。

## 小结

- LLM 应用的问题难以事后重现，必须在当时记下每一步的完整输入输出，串成追踪。
- 最重要的一条记录是模型实际收到的完整输入；调试时从它出发，按第 7 章的方法往前查。
- 追踪汇总成质量、延迟、成本、可靠性四类指标，延迟看分位数；出错的追踪转成测试用例。
