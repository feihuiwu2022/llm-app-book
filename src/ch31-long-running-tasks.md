# 31 长任务：检查点、恢复与人工介入

## 从一个问题开场

Agent 已经连续工作了四十分钟，改了二十几个文件。这时发生了下面任何一件事：

- 你发现它从第十分钟起就走错了方向；
- 网络断了，或者进程崩了；
- 它停下来问："要不要删掉旧的数据表？"而你在开会。

短任务里这些都不是问题，重来一遍就是了。任务一长，三个问题变得尖锐：**做错了能不能退回去？断了能不能接着做？需要人拿主意的时候怎么办？**

这三件事分别对应检查点、恢复、人工介入。它们是让 Agent 能被放心地交给长任务的前提。

## 手算一次：没有检查点的代价

一个 40 步的任务，每一步有 2% 的概率出现需要推倒重来的问题（方向错了、进程崩了）。

整个任务一次跑通的概率 = 0.98⁴⁰ ≈ **45%**

也就是说，一半以上的情况会在中途出事。出事之后：

| | 没有检查点 | 每 5 步一个检查点 |
|---|---|---|
| 出事后从哪开始 | 从头 | 最近的检查点 |
| 最多白做几步 | 39 | 4 |
| 平均白做几步（假设出事点均匀分布） | 约 20 | 约 2 |

检查点把一次失败的代价从"半个任务"降到"两三步"。任务越长，这个差别越大。

## 掰开：检查点

检查点是在某个时刻给状态拍的一张快照，之后可以退回到这一刻。

### 要拍什么

Agent 的状态有两部分，必须一起保存、一起恢复：

| 状态 | 是什么 | 只恢复它会怎样 |
|---|---|---|
| 对话状态 | 消息列表：模型知道自己做过什么 | 文件已经改了，模型却不知道，会重复修改 |
| 外部状态 | 文件、数据库、环境：实际做了什么 | 文件退回去了，模型却以为改过了，会跳过该做的事 |

两者不一致是长任务里很隐蔽的一类故障。

以 Claude Code 为例：它在每一轮用户输入开始时自动记录一个检查点，保存的是对话位置和文件快照。回退时可以选择只退对话、只退代码、或两者一起。

### 拍不到什么

这是理解检查点最重要的一点。还是以 Claude Code 为例，它的文档明确说检查点只跟踪由文件编辑工具做出的修改，以下内容不在范围内：

- shell 命令造成的改动：命令删掉的文件、改动的数据库；
- 外部系统里发生的事：已经发出的邮件、已经调用的接口、已经部署的服务；
- 子 Agent 所做的修改（有例外情况）；
- 会话之外、人手动做的修改。

文档的原话是检查点不能替代版本管理。

一般化地说：**检查点只能撤销它自己记录过的东西。世界上的大多数副作用是撤销不了的。**

这直接决定了权限该怎么设：

| 操作类型 | 能否撤销 | 对策 |
|---|---|---|
| 编辑工作目录里的文件 | 能，靠检查点 | 可以放手 |
| 本地 shell 命令 | 部分能，靠版本管理和沙箱 | 在隔离环境里放手 |
| 发消息、调外部接口、部署、付款 | 不能 | 必须事先确认（第 34 章） |

**可撤销的操作可以先做后审，不可撤销的操作必须先审后做。** 这一条是整章的核心。检查点的价值在于它扩大了"可以先做后审"的范围，让 Agent 在这个范围内不必步步请示。

## 掰开：恢复

恢复解决的是"断了之后接着做"。

第 2 章说模型是无状态的。这在恢复时成了优点：Agent 的全部状态就是消息列表加外部状态。只要把消息列表持久化到磁盘或数据库，进程崩了重启，读回来，再调一次模型，就接上了。模型不知道也不需要知道中间断过。

实现要点：

| 要点 | 原因 |
|---|---|
| 每一轮结束就落盘，不要等任务结束 | 崩溃发生在任务中途 |
| 记录每个工具调用的状态：已请求、执行中、已完成 | 崩溃可能发生在工具执行到一半时 |
| 工具尽量做成幂等的：执行两次和执行一次效果相同 | 恢复后不确定上一次是否执行成功，只能重试 |
| 保存的是完整会话，不只是摘要 | 第 23 章：摘要是有损的 |

第三行值得展开。恢复时发现最后一条记录是"请求创建工单"，没有结果。工单建了没有？不知道。如果"创建工单"不幂等，重试就会建出两张。办法是给每次调用带一个唯一编号，接收方见到重复的编号就返回上次的结果。这是分布式系统里的老问题，Agent 系统原样继承。

### 恢复之后的上下文

长任务往往会超过一个上下文窗口，恢复一个很长的会话时尤其如此。第 23 章的手段在这里汇合：

- 压缩后的摘要加上最近几轮的原文；
- 外部的待办清单和笔记，这是最可靠的"我做到哪了"；
- 版本管理里的提交记录，这是最可靠的"实际做了什么"。

一个实用的习惯是让 Agent 在长任务里定期把进度写进一个文件。即使会话完全丢失，一个新的 Agent 读这个文件加上提交记录，也能接手。

## 掰开：人工介入

长任务不等于无人值守。人介入的方式有四种，对应四个时机：

| 时机 | 方式 | 例子 |
|---|---|---|
| 动手之前 | 审批计划 | Agent 先只读地调研、给出方案，人同意后才开始修改 |
| 进行当中 | 审批单个操作 | 遇到未授权的操作时停下来请示 |
| 任何时候 | 打断和转向 | 人看到方向不对，中途喊停，补充一句要求后继续 |
| 完成之后 | 审阅结果 | 以差异或合并请求的形式交付，人逐项确认 |

### 权限模式：把介入程度做成档位

逐个操作审批最安全，也最烦人。一个长任务问上百次，人很快就不看内容直接点同意了，审批形同虚设。所以成熟的 harness 把"问多少"做成可切换的模式。以 Claude Code 为例：

| 模式 | 行为 | 适合 |
|---|---|---|
| 手动（默认） | 只读操作自动执行，其余逐个询问 | 不熟悉的任务、敏感的环境 |
| 自动接受编辑 | 文件修改和常见的文件操作自动执行，其余仍询问 | 信任它改代码，但命令要看一眼 |
| 计划 | 只调研和提方案，方案被批准前不能修改任何东西 | 大改动之前 |
| 自动 | 由一个分类器审查每个操作，安全的直接执行 | 长任务，希望少被打断 |
| 不询问 | 凡是需要询问的一律拒绝 | 无头运行、持续集成（第 30 章） |
| 跳过权限 | 全部执行 | 仅限隔离的容器或虚拟机 |

另有明确的允许和拒绝规则清单，拒绝规则在任何模式下都生效。

这个设计的要点是**自主程度可以随信任和风险调节**，而不是全有或全无。同一个任务里也可以切换：先用计划模式定方向，再切到自动接受编辑去执行。计划模式就是第 20 章"计划先给人过目"的产品形态。

### 请示要问得好

Agent 停下来问人的那句话，决定了人工介入的质量：

- 差的问法："是否继续？"
- 好的问法："准备删除旧表 `orders_v1`（共 12 万行，最近 90 天无写入）。删除后无法通过检查点恢复。是否执行？"

好的请示包含三样：要做什么、依据是什么、能不能撤销。人只凭这一句话就能做决定，不需要翻回去看上下文。

### 人不在的时候

开场第三种情况：Agent 需要决定，而人不在。几种处理：

| 处理 | 做法 |
|---|---|
| 等 | 保存状态，挂起，发通知；人回来后从原地继续。这要求上面的恢复能力 |
| 绕 | 先做不依赖这个决定的其他部分，把问题攒着 |
| 按保守的默认值做 | 事先约定：拿不准就选可撤销的那个选项 |
| 不做 | 第 27 章的观察模式：记下"我本来想做什么" |

不能接受的处理只有一种：因为没人回答，就自己替人做了那个不可撤销的决定。

## 后台运行

长任务里常有耗时的操作：跑一套测试要十分钟，构建要半小时。如果 Agent 的循环卡在等这个命令返回，这段时间它什么都做不了，也收不到人的新消息。

做法是把慢操作放到后台：工具立刻返回一个任务编号，Agent 继续做别的，操作完成时由 harness 通知它。第 27 章提到的 Super-agent 原型，据报道把运行超过几秒的命令自动转入后台，就是这个思路。

后台任务要求 Agent 能处理"异步到来的结果"：一条不是由它上一步直接引出的消息。这比严格的一问一答循环复杂，是常驻 Agent 和长任务 Agent 共有的工程难点。

## 为什么这样设计

三样机制解决的是同一个矛盾：希望 Agent 自主地做长时间的工作，又不能承受它出错的后果。检查点把一部分后果变成可撤销的；恢复让意外中断不等于前功尽弃；人工介入把不可撤销的决定留给人。合起来，它们划出了一个范围：在范围之内 Agent 可以放手去做，做错了有办法退回；范围之外必须停下来问。

第 28 章说 harness 的职责是"保证"。本章这三样是其中分量最重的部分。

## 优势、劣势、什么时候不该用

**优势**：长任务变得可行；失败的代价从整个任务降到几步；自主程度可调。

**劣势**：
- 检查点有盲区，容易给人"什么都能撤销"的错觉；
- 持久化、幂等、异步通知都增加了实现复杂度；
- 权限模式选得太松会出事，太紧则失去长任务的意义，需要按场景校准。

**不该用的时候**：几轮就结束的短任务。直接重跑比恢复更简单。

## 常见误解

**"有检查点，就可以放心让它做任何事。"** 检查点只覆盖它跟踪的那部分改动。发出去的消息、调过的外部接口退不回来。

**"恢复就是把聊天记录重新发一遍。"** 还要处理执行到一半的工具调用，以及对话状态和外部状态的一致。

**"人工确认越多越安全。"** 确认太多，人会不看就点。有效的做法是减少询问的数量，提高每次询问的信息量。

**"长任务应该一次交代清楚然后完全不管。"** 中途看一眼、纠正方向，是最便宜的质量保证。能打断和转向是长任务 harness 的必备能力。

## 小结

- 长任务需要三样东西：检查点让做错了能退回，持久化让断了能续上，人工介入把不可撤销的决定留给人。
- 检查点只能撤销它记录过的改动，外部副作用撤销不了；所以可撤销的操作先做后审，不可撤销的先审后做。
- 介入程度应做成可调的档位；请示要写明做什么、依据、能否撤销；没人回答时可以等、绕、取保守默认值，不能替人做不可撤销的决定。
