# 15 代码执行与结构化输出

## 从一个问题开场

两个看起来不相干的问题：

- 问模型"0.995 的 720 次方是多少"，它给出一个接近但不对的数。
- 让模型"只输出 JSON"，第 3 章测过，二十次里总有几次多写一句话，下游解析失败。

它们的病根相同：模型的输出是按概率一个 token 一个 token 抽出来的。算术需要每一位都对，JSON 需要每一个括号都对，而抽样天生不保证这一点。

两个问题的解法也是同一个思路：**不指望模型自己做对，把需要精确的部分交给确定性的程序。** 前者是代码执行，后者是结构化输出。

## 掰开：代码执行

代码执行是一个特殊的工具。它只有一个参数：一段代码。程序在隔离环境里运行这段代码，把输出返回给模型。

往返过程就是第 13 章的四步，只是工具换了：

| 步骤 | 内容 |
|---|---|
| 用户提问 | 0.995 的 720 次方是多少？ |
| 模型输出调用请求 | `run_python(code="print(0.995 ** 720)")` |
| 程序在沙箱里执行 | 输出 `0.027078…` |
| 模型写最终回复 | 约 0.027 |

分工很清楚：模型负责把问题翻译成代码，这是它擅长的；解释器负责算，这是模型不擅长而程序绝不出错的。

### 一个工具顶一百个

代码执行的价值不止于算术。对比两种给模型能力的方式：

| | 逐个定义工具 | 给一个代码执行环境 |
|---|---|---|
| 求平均值 | 写一个 `average` 工具 | 模型自己写一行代码 |
| 按条件筛选表格 | 再写一个 `filter` 工具 | 模型自己写 |
| 画一张图 | 再写一个 | 模型自己写 |
| 没预料到的需求 | 做不了 | 多半能写出来 |

数据分析类任务尤其合适：把文件放进沙箱，模型写代码读取、统计、作图，中间的大量数据不必经过上下文，只有最后的结论回到模型面前。

### 沙箱：必须有的那一层

运行模型写的代码，等于运行一段你没审过的代码。它可能写错，也可能因为读到了恶意内容而被诱导。所以执行环境必须隔离：

| 限制 | 防什么 |
|---|---|
| 文件系统隔离，只能看到指定目录 | 读走或删掉宿主机上的文件 |
| 默认不联网，或只允许访问白名单 | 把数据传出去、下载恶意程序 |
| 限制 CPU、内存、运行时长 | 死循环、耗尽资源 |
| 用完即销毁 | 一次任务的残留影响下一次 |

实现上通常是容器或轻量虚拟机。直接在业务服务器上 `exec` 模型给的代码，是典型的事故起因。

## 掰开：结构化输出

要让输出稳定地符合某种格式，有三档手段，强度递增：

### 第一档：在提示词里要求

写明格式、给示例。这是第 4 章的办法，成本最低，但只是提高概率。第 3 章的探针二测的就是这一档的合格率。

### 第二档：校验加重试

程序用解析器验收输出，不合格就把错误信息发回去让模型重写：

```text
你的输出无法解析为 JSON：第 1 行第 1 列出现意外字符"好"。请只输出 JSON，不要包含其他文字。
```

手算一下效果。假设单次合格率是 85%，允许重试两次（最多三次机会）：

- 三次全不合格的概率 = 0.15³ ≈ 0.0034
- 最终合格率 ≈ **99.7%**

代价是延迟和费用：15% 的请求要多调一次，约 2% 要多调两次，平均每个请求调用约 1.17 次。

### 第三档：约束解码

这一档直接改生成过程。第 2 章讲过，模型每一步算出所有 token 的概率再抽一个。约束解码在抽之前加一步：**把不符合格式的 token 的概率清零。**

假设要求的格式是：

```json
{ "level": "warning" 或 "error" 或 "info" }
```

模型已经写出了 `{"level": "`，下一个 token：

| 候选 token | 模型原始概率 | 是否符合格式 | 约束后 |
|---|---|---|---|
| `warning` | 0.55 | 是 | 0.55 → 重新归一后 0.59 |
| `error` | 0.30 | 是 | 0.30 → 0.32 |
| `info` | 0.08 | 是 | 0.08 → 0.09 |
| `严重` | 0.05 | 否 | 0 |
| `好的` | 0.02 | 否 | 0 |

归一就是把剩下三项除以它们的和 0.93。模型只能在合法的三个里选，无论抽到哪个，格式都是对的。每一步都这样过滤，最终输出必然能被解析，并且符合给定的字段和类型定义。

使用时，你提供一份 JSON Schema（字段名、类型、枚举值、哪些必填），服务端据此约束生成。第 13 章工具调用的参数也可以用同样的机制保证合法。

### 保证了什么，没保证什么

约束解码保证的是**形状**：一定是合法 JSON，字段齐全，类型正确，枚举值在范围内。

它不保证**内容**：`"level": "info"` 格式完全正确，但这条故障也许应该是 `error`。温度字段是整数没错，但填了 220。

所以形状靠约束，内容仍然要靠校验和评测。数值范围、字段之间的逻辑关系（结束时间晚于开始时间），要在程序里另行检查。

还有两个实际限制：

- 格式定义得太死，会挤掉模型思考的空间。需要推理的任务，可以在结构里留一个放推理过程的字段，并把它排在结论字段之前，让模型先想后答。
- 输出被 `max_tokens` 截断时，约束也救不了，JSON 仍然是残的。

## 两者的共同点

| | 代码执行 | 结构化输出 |
|---|---|---|
| 模型不可靠的地方 | 精确计算、数据处理 | 严格的格式 |
| 交给谁保证 | 解释器 | 语法约束 |
| 模型还负责什么 | 把问题翻译成代码 | 决定每个字段填什么内容 |

**让概率性的部件只做判断，让确定性的部件负责精确。** 这条原则在第 19 章设计 Agent 时还会反复用到。

## 优势、劣势、什么时候不该用

**代码执行**

- 优势：计算和数据处理绝对精确；一个工具覆盖大量长尾需求。
- 劣势：需要搭建和维护沙箱；多一轮往返；模型写的代码可能有逻辑错误，结果精确但答非所问。
- 不该用：任务不涉及计算和数据处理；没有条件做隔离。

**结构化输出**

- 优势：输出可以直接被程序消费，省掉解析失败的处理逻辑。
- 劣势：首次使用某个格式定义时可能有额外的准备耗时；支持的格式定义有限制；过度约束会降低内容质量。
- 不该用：输出是给人读的自然语言。

## 常见误解

**"模型数学不好，换个更强的就行。"** 更强的模型算得更准，但多位数运算仍然不保证每一位都对。需要精确结果时应该用工具。

**"开了结构化输出，结果就可靠了。"** 可靠的是格式。内容对不对是另一回事。

**"JSON 模式和结构化输出是一回事。"** 有些接口提供的"JSON 模式"只保证输出是合法 JSON，不保证符合你的字段定义。按字段定义约束的才是这里说的第三档。

**"沙箱是可选的优化项。"** 只要运行的代码不是你自己写的，隔离就是必需的。

## 小结

- 模型的抽样式输出天生不保证精确，计算交给代码执行，格式交给结构化输出。
- 代码执行让模型写代码、沙箱运行，是通用性最强的工具，前提是隔离到位。
- 结构化输出有提示词、校验重试、约束解码三档；约束解码保证形状，内容仍需校验。
