# 26 成本与延迟账本

> ▶ 本章配套代码：`code/ch26_cost.py`，只用 Python 标准库，可直接运行。

## 从一个问题开场

原型演示很成功。老板问了两个问题："上线后一个月要花多少钱？用户问一句要等几秒？"

前面各章都留了"资源账本"一节，零散地算过。本章把它们收拢成一套通用的算法：给定架构，能在纸上估出费用和延迟，并且知道哪几个旋钮能把它们降下来。

本章所有单价和速度都是为了演示而假设的整数，不是任何厂商的报价。请把配套代码开头的 `PRICE` 和 `SPEED` 换成你的合同价和实测值，公式不变。

## 掰开：钱是怎么算的

按量计费的模型服务，账单由三种 token 构成：

| 计费项 | 是什么 | 本章假设单价（元 / 百万 token） |
|---|---|---|
| 输入 | 发给模型的全部内容：系统提示词、工具清单、历史、资料、问题 | 10 |
| 缓存命中的输入 | 输入中与之前请求前缀相同、命中缓存的部分 | 1 |
| 输出 | 模型生成的全部内容，包括推理模型的思考内容 | 40 |

**一次调用的费用 = 未命中的输入 × 输入单价 + 命中的输入 × 缓存单价 + 输出 × 输出单价**

两个普遍规律，具体倍数各家不同：

- 输出单价是输入的数倍。第 2 章讲过原因：输入一次读完，输出要逐个生成。
- 缓存命中的输入远比普通输入便宜。有的服务商写入缓存时另收少量费用。

## 手算一：三种架构回答同一个问题

回答一个手册问题，输出都是 200 token。配套代码的输出：

```text
一、单次调用：三种架构回答同一个问题（输出都是 200 token）
  裸问（不带资料）       输入     100 token  费用 0.0090 元  每天一万次       90 元
  RAG（5 块 × 400 字） 输入    2100 token  费用 0.0290 元  每天一万次      290 元
  整本手册放进上下文      输入  200100 token  费用 2.0090 元  每天一万次    20090 元
  整本手册 + 缓存命中    输入  200100 token  费用 0.2090 元  每天一万次     2090 元
```

拿 RAG 那一行验算：

- 输入：2,100 × 10 ÷ 1,000,000 = 0.021 元
- 输出：200 × 40 ÷ 1,000,000 = 0.008 元
- 合计 **0.029 元**

几点观察：

- 裸问时费用的大头是输出（0.008 对 0.001）；加了资料后大头变成输入。优化方向因此不同。
- 整本放入比 RAG 贵约 69 倍；开了缓存后贵约 7 倍。这是第 9 章选型的数字依据。
- 单次看都是几分钱，乘以调用量之后差距是每天几百元对几万元。

## 手算二：Agent 的累加

第 17、19、21 章反复提到：Agent 每一轮都把之前的全部内容重发一遍。

设固定前缀（系统提示词加工具清单）为 F，每轮新增进上下文的量为 a，共跑 N 轮。第 n 轮的输入是 F + (n − 1) × a，所以：

**累计输入 = N × F + a × N × (N − 1) ÷ 2**

取 F = 2,000，a = 1,500，N = 10：

- N × F = 20,000
- a × N × (N − 1) ÷ 2 = 1,500 × 45 = 67,500
- 累计输入 = **87,500 token**

后一项里有 N 的平方。配套代码的输出：

```text
二、Agent：输入随轮数累加（固定前缀 2000，每轮新增 1500，每轮输出 300）
   1 轮  累计输入    2000 token  费用 0.0320 元  开缓存 0.0320 元  串行耗时 6.8 秒
   5 轮  累计输入   25000 token  费用 0.3100 元  开缓存 0.1570 元  串行耗时 34.0 秒
  10 轮  累计输入   87500 token  费用 0.9950 元  开缓存 0.3470 元  串行耗时 68.0 秒
  20 轮  累计输入  325000 token  费用 3.4900 元  开缓存 0.8395 元  串行耗时 136.0 秒
```

轮数从 10 到 20 翻一倍，累计输入从 8.75 万到 32.5 万，变成 3.7 倍。**Agent 的费用随轮数近似按平方增长。** 这是必须设轮数上限、必须做上下文管理的数字原因。

再看"开缓存"那一列。Agent 的每一轮输入，都以上一轮的输入为前缀，只是末尾多了一段。这正是提示缓存最适合的形态：前面的大部分都能命中。20 轮时，缓存把费用从 3.49 元降到 0.84 元，约四分之一。对 Agent 来说，提示缓存是最重要的单项成本优化。

## 掰开：时间是怎么算的

一次模型调用的耗时分两段：

**耗时 = 首字延迟 + 输出 token 数 ÷ 输出速度**

- **首字延迟**：从发出请求到收到第一个 token 的时间。包括网络、排队和模型读完输入的时间。输入越长越久，命中缓存时明显缩短。
- **输出速度**：每秒生成多少个 token。

假设首字延迟 0.8 秒，输出速度每秒 50 token：

```text
三、延迟：输出长度决定耗时
  输出   50 token  耗时 1.8 秒
  输出  200 token  耗时 4.8 秒
  输出 1000 token  耗时 20.8 秒
```

**决定总耗时的主要是输出长度。** 1000 token 的回答要 20 秒，其中 20 秒是在逐个生成。

整条链路的延迟是各段相加。以第 24 章那条追踪为例：嵌入 20 + 召回 35 + 重排 180 + 拼装 15 + 生成 2100 = 2350 毫秒。

Agent 的延迟是每一轮相加，再加上工具执行时间。上表的"串行耗时"只算了模型调用，每轮输出 300 token 是 6.8 秒，20 轮就是两分多钟。

### 用户感受到的延迟

同样是 5 秒，一次性显示和逐字显示的体验完全不同。流式输出让用户在首字延迟之后就开始阅读，感知到的等待从"总耗时"变成了"首字延迟"。对交互式应用，这通常是性价比最高的体验优化。

它不改变总耗时。如果下游是程序而不是人，流式没有帮助。

## 怎么测

估算用公式，上线前必须实测。每次请求记录四个数（第 24 章的追踪里都有）：

| 测什么 | 怎么取 |
|---|---|
| 输入、输出、缓存命中 token 数 | 接口响应里的用量字段，不要自己估 |
| 首字延迟 | 流式接口下，发出请求到收到第一段内容的时间差 |
| 总耗时 | 发出请求到收完的时间差 |
| 输出速度 | 输出 token 数 ÷ (总耗时 − 首字延迟) |

注意三点：

- 用真实分布的请求测，不要只测一条；
- 看中位数和 95 分位，不看平均值；
- 在预期的并发量下测。单条请求快，不代表高峰期也快。

本书一直按"1 个汉字约 1 个 token"粗算。实际比例因模型的分词器而异，账单以接口返回的用量为准。

## 降本提速的旋钮

按投入从小到大排列：

| 旋钮 | 降什么 | 做法 | 代价 |
|---|---|---|---|
| 限制输出长度 | 费用、延迟 | 提示词里要求简短；设合理的 `max_tokens` | 可能截断 |
| 流式输出 | 感知延迟 | 打开流式 | 无 |
| 提示缓存 | 费用、首字延迟 | 稳定内容放前面，易变内容放后面 | 要注意前缀稳定性 |
| 精简输入 | 费用 | 少取几块；清理工具清单；清理旧工具结果 | 可能丢信息 |
| 并行 | 延迟 | 互不依赖的工具调用和子任务同时执行 | 总费用不变或更高 |
| 模型分级 | 费用、延迟 | 简单任务用小模型，困难任务才用大模型 | 要做分流，小模型质量低 |
| 批量接口 | 费用 | 不要求实时的任务走异步批量，通常有折扣 | 结果延后 |
| 控制思考预算 | 费用、延迟 | 推理模型按任务难度设置思考量 | 难题可能想不够 |
| 减少轮数 | 费用、延迟 | 更好的工具设计；一轮内并行调用；设上限 | 需要调优 |
| 蒸馏到小模型 | 费用、延迟 | 第 11、12 章 | 一次性投入大 |

顺序有讲究：前五项几乎没有质量损失，应该先做；后面几项要用第 23 章的评测确认质量没有下降。

## 为什么这样设计

按 token 计费反映的是真实的计算消耗：每个输入 token 都要过一遍模型，每个输出 token 都要单独算一次。所以省钱的办法归根到底只有三种：让模型少读、少写，或者换一个每个 token 更便宜的模型。上面所有旋钮都是这三种的具体形式。

自己部署模型时，账从按 token 变成按硬件和电费，算法见第一卷「资源账本」篇。

## 常见误解

**"token 单价年年降，不用关心成本。"** 单价在降，用量涨得更快。从单次问答到 Agent，一个任务的 token 用量可以相差上百倍。

**"输入便宜，多放点没关系。"** 单价便宜，但量大。RAG 和 Agent 的账单里，输入通常占大头。

**"换成更快的模型，延迟问题就解决了。"** 先看时间花在哪。Agent 跑了 20 轮，瓶颈是轮数；输出了 2000 字，瓶颈是输出长度。

**"平均每次几分钱，成本可控。"** 要看分布。少数跑了几十轮的 Agent 任务可能占掉大半费用。给单个任务设费用上限。

## 小结

- 费用 = 输入、缓存命中输入、输出三项各乘单价；输出单价高，但 RAG 和 Agent 里输入量大，往往是大头。
- Agent 的累计输入是 N × F + a × N × (N − 1) ÷ 2，随轮数近似平方增长；提示缓存对它最有效。
- 耗时 = 首字延迟 + 输出长度 ÷ 输出速度；先用公式估算，再用真实请求实测，看 95 分位。
